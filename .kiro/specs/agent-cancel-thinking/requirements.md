# 需求文档

## 简介
DBAgent 当前在用户提交问题后，Agent 进入 ReAct 循环（思考→工具调用→观察→继续），用户必须等待整个过程完成或达到最大迭代次数（15轮）才能看到最终结果。当 Agent 思考时间过长、工具调用卡住或用户意识到问题描述有误时，用户无法中断当前执行，只能被动等待或刷新页面，体验差且浪费 LLM 资源。

本功能为 DBAgent 增加用户主动终止 Agent 执行的能力：用户在回答过程中点击"停止"按钮后，系统立即终止 ReAct 循环，保留已产生的思考文本和工具调用记录，返回部分结果给用户，同时保持会话状态的完整性。

## 边界上下文
- **范围内**：用户在 Agent 执行过程中触发取消操作；ReAct 循环在安全点终止；保留已产生的思考文本和工具调用记录；前端展示取消状态和部分结果；取消后会话状态完整可恢复；支持 SSE 和 WebSocket 两种传输协议
- **范围外**：回滚已发送的 LLM 请求（token 已消耗无法撤回）；回滚已执行的数据库操作（副作用已产生）；取消后的自动重试机制；取消操作的权限控制（当前所有用户均可取消自己的请求）
- **相邻预期**：现有 SSE 流和 WebSocket 连接管理机制保持不变；会话存储（SQLite）继续正常持久化状态；OpenViking 语义记忆和偏好记录继续正常工作；Agent 执行引擎（ReAct 循环）继续驱动 LLM 决策和工具调用

## 需求

### 需求 1：用户主动终止 Agent 执行
**目标：** 作为用户，我希望在 Agent 思考或执行工具调用期间点击"停止"按钮，以便在等待时间过长或问题描述有误时立即中断当前执行。

#### 验收标准
1. When 用户在 Agent 执行过程中触发取消操作，the 系统 shall 在下一个安全点终止 ReAct 循环
2. When 取消请求到达时 Agent 正在等待 LLM 响应，the 系统 shall 中断等待并立即终止
3. When 取消请求到达时 Agent 正在执行工具调用，the 系统 shall 等待当前工具执行完成后终止（不中断进行中的数据库操作）
4. When 取消完成后，the 系统 shall 向客户端发送取消事件，与正常完成事件区分
5. If 取消请求到达时 Agent 已完成执行，then the 系统 shall 忽略取消请求（幂等操作）

### 需求 2：取消后部分结果保留
**目标：** 作为用户，我希望取消后能看到 Agent 已产生的思考内容和工具调用记录，以便了解执行进度并决定是否重新提问。

#### 验收标准
1. When Agent 执行被取消，the 系统 shall 保留已产生的思考文本并返回给客户端
2. When Agent 执行被取消，the 系统 shall 保留已完成工具调用的记录（包含工具名称和结果）
3. When Agent 执行被取消，the 系统 shall 将已有的思考文本和工具调用记录追加到会话历史中
4. When 取消时无任何产出（首轮 LLM 调用尚未返回），the 系统 shall 返回空结果并正常结束本轮对话

### 需求 3：取消状态的前端反馈
**目标：** 作为用户，我希望在点击"停止"后能看到明确的状态变化，以便确认取消操作已生效。

#### 验收标准
1. When 用户触发取消操作，the 系统 shall 在前端立即显示"正在取消"状态
2. When 取消完成，the 系统 shall 将连接状态徽章从"运行中"切换为"已取消"
3. When 取消完成，the 系统 shall 恢复发送按钮可用状态，允许用户继续输入新消息
4. When 取消完成，the 系统 shall 在消息区域展示取消提示信息

### 需求 4：多传输协议兼容
**目标：** 作为系统，我希望取消功能在 SSE（HTTP 流）和 WebSocket 两种传输协议下均能正常工作，以便覆盖所有用户接入方式。

#### 验收标准
1. When 用户通过 SSE 连接使用系统，the 系统 shall 支持用户点击停止按钮触发取消
2. When WebSocket 客户端断开连接，the 系统 shall 自动终止该会话正在执行的 Agent 任务
3. When 客户端通过 HTTP 取消端点发送取消请求，the 系统 shall 接受并处理取消操作

### 需求 5：取消后会话状态完整性
**目标：** 作为用户，我希望取消操作不破坏会话状态的一致性，以便在取消后继续同一会话或切换到其他会话。

#### 验收标准
1. When Agent 执行被取消，the 系统 shall 将已产生的对话内容持久化到会话存储中
2. When 取消后刷新页面或重新进入会话，the 系统 shall 恢复取消前的完整对话历史（包含用户消息和已产出的 Agent 回复内容）
3. When 取消后用户发送新消息，the 系统 shall 正常开始新的 Agent 执行，不受之前取消操作影响
4. The 系统 shall 确保取消操作不影响其他活跃会话的 Agent 执行

### 需求 6：异常场景静默降级
**目标：** 作为系统运维者，我希望取消功能在异常情况下不影响核心对话流程，以便系统保持稳定可用。

#### 验收标准
1. When 取消信号传递过程中发生异常，the 系统 shall 静默降级，Agent 继续正常执行至完成
2. When 取消后会话状态保存失败，the 系统 shall 记录错误日志但不影响用户后续操作
3. When 同一会话连续多次触发取消，the 系统 shall 仅处理首次有效的取消请求
