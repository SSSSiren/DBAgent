# asyncio.wait → 轮询 优化对比分析

**测试时间**: 2026-07-29
**用例**: 10 条 TC（001-029 精选）
**并发度**: 4

## 改动摘要

`app/agent/runner.py` 中 ReAct 循环的 LLM 调用部分：
- **改前**: `asyncio.create_task` × 2 + `asyncio.wait` 竞速（每次 LLM 调用创建 2 个 Task + 取消清理）
- **改后**: `asyncio.ensure_future` + `asyncio.sleep(0.05)` 轮询 `cancel_event`

## 结论

1. **asyncio.wait → 轮询优化效果有限** — repeat=4 时降低 12%，repeat=8 时反而略增。TTFB/Token/工具调用均未变化，说明 LLM 调用层的开销不是瓶颈。

2. **延迟增长根因仍是 eval 框架** — TTFB 完全稳定在 4.1s，Agent 内部效率无退化，但总延迟随 repeat 线性增长。这是 `asyncio.gather` 一次性创建所有任务 + Semaphore 排队导致的——属于评测框架固有特性，不是 Agent 性能退化。

3. **prep_ms 修复生效** — 从 0ms 变为 8-9ms，反映 context 构建耗时真实采集成功。

4. **建议**：如果要降低评测总耗时，增加 concurrency（如 8）来减少 Semaphore 排队时间，而非尝试在 Agent 内部优化。
