# 三大 Text-to-SQL Benchmark 对 Agent SQL 能力的测试适用性分析

## 1. 分析框架：Agent SQL 能力 vs LLM SQL 能力

在分析之前，先明确一个关键区分——**LLM 的 SQL 能力**和 **Agent 的 SQL 能力**是两类不同的能力维度：

| 能力维度 | LLM 模式 | Agent 模式 |
|----------|---------|-----------|
| 输入 | 一次性喂入完整 schema + question | 逐步探索、按需获取信息 |
| 交互 | 单轮：question → SQL | 多轮：探索 → 规划 → 执行 → 验证 → 修正 |
| 错误处理 | 无（一次性输出） | 捕获执行错误 → 分析原因 → 重试 |
| 结果验证 | 无（无法执行） | 执行 SQL → 检查结果 → 判断是否合理 |
| 复杂任务 | 一次性生成复杂 SQL | 分解为子查询 → 逐步执行 → 组合结果 |
| 效率优化 | 无 | 执行 → 分析耗时 → 重写优化 |

### Agent 的核心能力拆解

一个合格的 SQL Agent 应具备以下能力：

1. **Schema 探索**（Explore）：在不知道完整 schema 时，通过 `SHOW TABLES`、`DESCRIBE`、采样查询等方式自主发现数据库结构
2. **任务规划**（Plan）：将复杂自然语言问题分解为多个子步骤
3. **工具调用**（Tool Use）：调用 `execute_sql`、`get_table_info`、`sample_data` 等工具
4. **执行反馈**（Feedback Loop）：拿到 SQL 执行结果后，判断是否需要调整
5. **错误恢复**（Error Recovery）：SQL 语法错误/语义错误后，分析并修正
6. **结果验证**（Verification）：检查结果是否回答了原始问题
7. **效率优化**（Optimization）：分析查询耗时，重写低效 SQL
8. **外部知识整合**（Knowledge Integration）：结合领域知识进行推理

## 2. 逐项分析

### 2.1 Spider 1.0

**概述**：10,181 条问题，200 个 SQLite 数据库，经典学术基准。

#### 对 Agent 各能力的覆盖情况

| Agent 能力 | 覆盖程度 | 说明 |
|------------|:---:|------|
| **Schema 探索** | ❌ 不适用 | `tables.json` 一次性提供完整 schema，无需探索 |
| **任务规划** | ❌ 不适用 | 所有问题都是单步 SQL，无需分解 |
| **工具调用** | ❌ 不适用 | 不需要调用任何工具，模型直接输出 SQL |
| **执行反馈** | ❌ 不适用 | 评估时虽执行 SQL，但模型不参与执行→反馈→修正的循环 |
| **错误恢复** | ❌ 不适用 | 模型不感知执行结果，无法修正 |
| **结果验证** | ❌ 不适用 | 模型不验证自己的输出 |
| **效率优化** | ❌ 不适用 | 无效率评估维度 |
| **外部知识整合** | ❌ 不适用 | 无外部知识字段，仅依赖 schema |

#### 结论

**Spider 1.0 不适合测试 Agent 能力**。它是一个纯粹的 LLM 基准：给定 schema + 问题，一次性生成 SQL。所有信息都在 prompt 中，不存在探索、反馈、修正等 Agent 核心行为。

它的设计哲学是"如果模型能理解 schema 并生成正确 SQL，就说明它有 Text-to-SQL 能力"——这测的是 LLM 的语义理解和 SQL 生成能力，不是 Agent 能力。

#### 适用场景

- ✅ 测试 LLM 的 schema 理解 + SQL 生成基线能力
- ✅ 对比不同 LLM 的 Text-to-SQL 基础能力
- ❌ 不适合测试 Agent 能力

---

### 2.2 Spider 2.0

**概述**：ICLR 2025 Oral，615 个任务，企业级数据库（Snowflake、BigQuery、SQLite），含 DBT 代码代理任务。

#### 对 Agent 各能力的覆盖情况

| Agent 能力 | 覆盖程度 | 说明 |
|------------|:---:|------|
| **Schema 探索** | ⚠️ 部分适用 | 企业数据库 schema 庞大，模型可能需要选择性探索相关表。但 Spider 2.0 的问题中标注了 `tables` 字段，缩小了范围 |
| **任务规划** | ⚠️ 部分适用 | Snow/Lite 是单步 SQL，但 DBT 任务（68 个）是仓库级代码代理任务，需要多步规划 |
| **工具调用** | ⚠️ 部分适用 | `spider-agent-tc`（tool-call）模式天然支持工具调用；DBT 任务需要代码代理 |
| **执行反馈** | ⚠️ 部分适用 | 在 Spider-Agent 框架中，Agent 可以执行 SQL 并获取反馈 |
| **错误恢复** | ⚠️ 部分适用 | 企业数据库的 SQL 复杂性高，容易出错，Agent 需要理解错误信息并修正 |
| **结果验证** | ⚠️ 部分适用 | 大规模数据下，Agent 可能需要验证结果合理性 |
| **效率优化** | ❌ 不适用 | 无效率评估维度；Snowflake 免费但查询排队 |
| **外部知识整合** | ⚠️ 部分适用 | `evidence` 字段提供外部知识，但这是预标注的，不需要 Agent 自行检索 |

#### 关键差异：三种任务设置的分析

| 任务设置 | Agent 适用性 | 分析 |
|----------|:---:|------|
| **Spider 2.0-Snow** | 🟡 中等 | Tool-call 模式支持 Agent 工作流，但本质仍是 Text-to-SQL |
| **Spider 2.0-Lite** | 🟡 中等 | 跨多种数据库方言，Agent 需要适配不同 SQL 方言 |
| **Spider 2.0-DBT** | 🟢 较好 | 明确设计为代码代理任务，需要多步操作、仓库级理解 |

#### 结论

**Spider 2.0 有测试 Agent 能力的潜力，但主要优势在 DBT 子任务**。Snow 和 Lite 任务本质上仍是 Text-to-SQL，只是数据库规模更大、方言更多。Spider-Agent 框架提供了 Agent 测试的基础设施，但任务设计本身并非为 Agent 量身定制。

#### 适用场景

- ✅ 测试 Agent 在企业级数据库环境下的 SQL 生成能力
- ✅ 测试 Agent 跨多种数据库方言的适配能力
- ✅ DBT 子任务可测试代码代理的多步推理能力
- ⚠️ 需要自行搭建 Agent 框架（官方提供了 `spider-agent-tc` 等基础框架）
- ❌ 不测试效率优化和结果验证能力

### 2.3 BIRD

**概述**：NeurIPS 2023，12,751 条问题，95 个数据库（33.4 GB），强调数据库值和效率。

#### 对 Agent 各能力的覆盖情况

| Agent 能力 | 覆盖程度 | 说明 |
|------------|:---:|------|
| **Schema 探索** | ⚠️ 部分适用 | 提供了 `database_description/` 和 `columns.csv`，但 Agent 可以忽略这些，自行通过 `SELECT * LIMIT 1` 等方式探索数据库内容 |
| **任务规划** | ⚠️ 部分适用 | 复杂问题（challenging 级）可能需要多步推理 |
| **工具调用** | ⚠️ 部分适用 | Agent 可以调用 SQL 执行工具来探索数据库值 |
| **执行反馈** | ⚠️ 部分适用 | 评估时执行 SQL，Agent 可以利用反馈 |
| **错误恢复** | 🟡 中等 | 脏数据、非标准格式容易导致 SQL 错误，Agent 需要修正 |
| **结果验证** | 🟡 中等 | 大规模数据下结果可能不直观，需要验证 |
| **效率优化** | 🟢 强 | **VES/R-VES 是 BIRD 独有的效率评估维度**，Agent 可以在执行后分析耗时并重写优化 |
| **外部知识整合** | ⚠️ 部分适用 | `evidence` 字段提供外部知识，但 Agent 可以自行从数据库内容中推理 |

#### BIRD 对 Agent 最独特的价值：效率评估

BIRD 是三个基准中**唯一引入效率评估的基准**。VES（Valid Efficiency Score）和 R-VES（Reward-based VES）要求 SQL 不仅正确，还要高效：

```
R-VES 计算方式：
- 预测 SQL 执行时间 ≤ 黄金 SQL 执行时间 → 满分
- 预测 SQL 执行时间 > 黄金 SQL 执行时间 → 按比例扣分
```

这天然适合 Agent 模式：**Agent 生成 SQL → 执行 → 发现太慢 → 分析原因 → 重写优化 SQL**。这是一个典型的 Agent 反馈循环。

#### BIRD 的另一个 Agent 适用场景：值推理

BIRD 强调模型需要理解数据库中的实际值。对于 Agent 来说，这意味着可以：
- 执行 `SELECT DISTINCT column FROM table` 来了解列的取值范围
- 执行 `SELECT * FROM table LIMIT 5` 来查看数据格式
- 发现缩写/拼写错误后调整 SQL

#### 结论

**BIRD 在三个基准中具有最强的 Agent 测试潜力**，尤其是效率评估（VES）和值推理需求。但目前官方设计仍是单轮 Text-to-SQL 模式，需要自行将 Agent 工作流叠加到评估流程上。

#### 适用场景

- ✅ 测试 Agent 的 SQL 效率优化能力（VES 天然适合）
- ✅ 测试 Agent 的值探索和脏数据处理能力
- ✅ 测试 Agent 的反馈循环（执行→发现慢→优化）
- ⚠️ 需要自行设计 Agent 工作流（官方只提供 LLM 基线）
- ⚠️ 33.4 GB 数据，对 Agent 的探索效率要求高

## 4. 核心结论

### 4.1 Spider 1.0：仅适合 LLM，不适合 Agent

**Spider 1.0 是一个纯 LLM 基准，不应该用于测试 Agent 能力**。原因很简单：所有信息（schema、问题）都在一次性 prompt 中提供，模型不需要探索、不需要反馈、不需要修正。用 Spider 1.0 测 Agent 就像用单选题测编程能力——测的东西不对。

**但如果你的目标是测试 Agent 的基础 SQL 生成能力**（作为 Agent 流水线的一个环节），Spider 1.0 仍然有价值：它简单、下载即用、数据量适中，适合快速验证 Agent 中的 LLM 是否具备基本的 schema 理解和 SQL 生成能力。

### 4.2 Spider 2.0：部分适合 Agent，但性价比有限

Spider 2.0 的优势在于：
- 提供了官方 Agent 框架（`spider-agent-tc`、`spider-agent-lite`、`spider-agent-snow`）
- DBT 子任务明确设计为代码代理任务
- 企业级数据库环境的真实感

但局限性也很明显：
- Snow/Lite 任务本质仍是 Text-to-SQL，不是 Agent 任务
- 需要 Snowflake/BigQuery 账号，上手成本高
- 无效率评估，Agent 的优化能力无处体现

**建议**：如果你的 Agent 需要处理企业级多数据库方言场景，Spider 2.0-Lite 值得考虑。但仅从 Agent 能力测试的角度，性价比不如 BIRD。

### 4.3 BIRD：最适合改造为 Agent 测试基准

BIRD 是最适合测试 Agent 能力的基准，理由如下：

1. **效率评估（VES）天然适合 Agent 反馈循环**：Agent 生成 SQL → 执行 → 发现慢 → 优化 → 再执行。这是最自然的 Agent 工作流
2. **值推理需求适合 Agent 的探索行为**：Agent 可以先 `SELECT * LIMIT 5` 看看数据长什么样，再生成 SQL
3. **脏数据场景适合 Agent 的错误恢复**：SQL 报错 → Agent 分析错误 → 发现是数据格式问题 → 调整 SQL
4. **Mini-Dev 提供低门槛入口**：500 条数据即可验证 Agent 能力
5. **数据规模（33.4 GB）挑战 Agent 的探索效率**：Agent 不能盲目 `SELECT *`，需要智能采样

### 4.4 最终建议

```
┌──────────────────────────────────────────────────────────────────┐
│                     Agent SQL 能力测试路线图                        │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段 1：基础 SQL 生成能力验证                                     │
│    → 使用 Spider 1.0                                              │
│    → 目的：确保 Agent 中的 LLM 具备基本的 schema 理解和 SQL 生成     │
│    → 方式：将 Spider 1.0 的 question + schema 作为 Agent 的输入     │
│                                                                  │
│  阶段 2：Agent 核心能力验证                                        │
│    → 使用 BIRD（Mini-Dev 入手）                                    │
│    → 目的：测试探索、反馈、修正、优化等 Agent 核心能力                │
│    → 方式：只给 Agent 数据库连接，不给 schema 描述，让 Agent 自行探索  │
│                                                                  │
│  阶段 3：企业级 Agent 能力验证                                      │
│    → 使用 Spider 2.0-Lite 或 Spider 2.0-DBT                        │
│    → 目的：测试 Agent 在多数据库方言、企业级环境下的表现              │
│    → 方式：使用官方 Spider-Agent 框架                               │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 5. 对 BIRD 改造为 Agent 基准的具体建议

如果将 BIRD 改造为 Agent 测试基准，以下是具体改造方案：

### 5.1 输入改造

| 原始输入 | Agent 改造后 |
|----------|------------|
| 提供 `database_description/*.csv` | **不提供**，只给数据库连接，Agent 自行探索 |
| 提供 `evidence` 字段 | **不提供**，Agent 需要从数据库内容中推理 |
| 提供完整 `tables.csv` | **不提供**，Agent 需要 `SHOW TABLES` 自行获取 |

### 5.2 评估改造

| 原始评估 | Agent 改造后 |
|----------|------------|
| 单次 SQL 生成 → EX 评分 | 多轮交互 → 最终 SQL 的 EX 评分 |
| VES 基于单次执行时间 | VES 基于 Agent 最终优化后的 SQL 执行时间 |
| 不计入探索成本 | 计入 Agent 的探索步数、token 消耗、总耗时 |

### 5.3 新增评估维度

| 维度 | 说明 |
|------|------|
| **探索效率** | Agent 用了多少步才找到正确的表和列 |
| **Token 消耗** | 探索过程中消耗的 token 总量 |
| **纠错能力** | Agent 从错误中恢复的次数和成功率 |
| **优化增益** | Agent 优化后 SQL 相比初版的效率提升比例 |

---

## 6. 总结

| 结论 | 说明 |
|------|------|
| Spider 1.0 适合测试 LLM 基础能力 | 不应该用于 Agent 测试，但可以作为 Agent 流水线中 LLM 环节的快速验证 |
| Spider 2.0 有 Agent 框架但任务设计偏 Text-to-SQL | DBT 子任务最有 Agent 测试价值，但整体性价比不如 BIRD |
| **BIRD 最适合改造为 Agent 测试基准** | VES 效率评估 + 值推理 + 脏数据 = 天然适合 Agent 工作流 |
| 三个基准可以互补使用 | 建议按"Spider 1.0 → BIRD → Spider 2.0"的顺序逐步升级 Agent 能力测试 |
